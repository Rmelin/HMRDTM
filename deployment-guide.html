01
Ca. 10 minutter

Forbered NAS'en

Log ind i UGOS Pro lokalt, installér Docker-appen, og opret en projektmappe. Opdatér NAS og Docker, før løsningen får en offentlig webadresse.

Installér DockerFind Docker i App Center i UGOS Pro.
Opret projektmappeFx docker/hmrdtm.
Begræns adgangKun driftsbrugeren skal have skriveadgang.
Planlæg backupData skal ligge på vedvarende lager.
Stop og kontrollér

Aktivér ikke UPnP, DMZ eller port forwarding. Ved en stram firewall skal udgående TCP/UDP på port 7844 være tilladt.

02
Filer og hemmeligheder

Placér kun produktionsfilerne

Du behøver ikke kopiere hele udviklingsmappen. Opret én fast projektmappe på NAS'en, og overfør kun filerne nedenfor. Docker henter selv Node-pakker og bygger appen.

Placering i UGOS Files: docker/hmrdtmVia SSH kan den samme mappe fx hedde /volume1/docker/hmrdtm. Den præcise volume-sti kan være anderledes på din NAS; brug stien, UGOS viser for den delte docker-mappe.
Minimal struktur på NAS'en
docker/hmrdtm/
├── .dockerignore
├── .env                 # oprettes på NAS'en — hemmelig
├── .env.example
├── compose.production.yml
├── Dockerfile
├── docker-entrypoint.sh
├── package.json
├── package-lock.json
├── next.config.mjs
├── next-env.d.ts
├── tsconfig.json
├── drizzle/             # alle SQL-migrationer
├── public/              # ikon og offentlige filer
├── src/                 # selve appen
├── data/                # beholdes mellem opdateringer
└── backups/             # beholdes mellem opdateringer
✓ Kopiér til NAS'en
  • src/, public/ og drizzle/
  • Dockerfile, entrypoint og production Compose
  • package.json og package-lock.json
  • Next.js- og TypeScript-konfigurationen
  • .dockerignore og første gang .env.example
× Kopiér ikke
  • node_modules/ og .next/
  • .git/, .DS_Store og editorfiler
  • compose.yaml til lokal udvikling
  • lokale data/ og backups/
  • README, kravfiler og øvrig udviklingsdokumentation
Mac/Linux · lav en minimal pakke i projektmappen
tar --exclude='.DS_Store' --exclude='*/.DS_Store' \
  -czf hmrdtm-deploy.tar.gz \
  .dockerignore .env.example compose.production.yml Dockerfile docker-entrypoint.sh \
  package.json package-lock.json next.config.mjs next-env.d.ts tsconfig.json \
  drizzle public src

Kopiér hmrdtm-deploy.tar.gz til NAS'en, og pak den ud i projektmappen. Opret derefter de to vedvarende mapper og den private miljøfil:

NAS/SSH · første installation
mkdir -p /sti/til/docker/hmrdtm/data /sti/til/docker/hmrdtm/backups
tar -xzf hmrdtm-deploy.tar.gz -C /sti/til/docker/hmrdtm
cd /sti/til/docker/hmrdtm
cp .env.example .env
chmod 600 .env
Ved senere opdateringer

Udpak den nye produktionspakke oven i projektmappen, men slet eller erstat aldrig .env, data/ eller backups/. Produktionspakken indeholder dem netop ikke.

Hemmelighed og persondata

Del aldrig .env, commit den ikke til Git, og vis ikke tunnel-tokenet i screenshots. data/ og backups/ kan indeholde personoplysninger og må heller ikke indgå i overførselspakken.

03
Cloudflare

Opret tunnelen

  1. 1
    Opret en fjernadministreret tunnel

    I Cloudflare: Networking → Tunnels → Create tunnel. Vælg Cloudflared, og kald den fx hmrdtm-nas.

  2. 2
    Kopiér kun tokenet

    Vælg Docker som miljø. Kopiér værdien efter --token, og indsæt den som CLOUDFLARE_TUNNEL_TOKEN i .env.

  3. 3
    Tilføj en publiceret applikationsrute

    Vælg fx mad.ditdomæne.dk, og sæt servicen til:

    Type HTTPhttp://hmrdtm:3000
!

Hvorfor ikke localhost? cloudflared og appen er separate containere. Tunnelen finder appen på Compose-servicenavnet hmrdtm.

04
Docker Compose

Byg og start containerne

Brug NAS'ens Docker-GUI nedenfor. Terminalkommandoerne er et alternativ, hvis du foretrækker SSH.

UGOS Pro · Docker GUI

Deploy som Project — uden terminal

Projektmappen skal allerede indeholde projektets filer, herunder compose.production.yml og den beskyttede .env-fil fra trin 2.

  1. Åbn Docker og vælg ProjectLog ind i UGOS Pro som NAS-administrator. Åbn App Center → Docker, vælg derefter fanen Project.
  2. Vælg CreateOpret et nyt Compose-projekt. Giv det navnet hmrdtm, så det er let at genkende ved opdateringer.
  3. Indlæs Compose-filenVælg Upload Compose file eller indsæt filindholdet, afhængigt af UGOS-versionen. Brug compose.production.yml fra projektmappen.
  4. Tilføj tunnel-tokenet sikkertHvis guiden viser et felt for miljøvariabler, tilføj CLOUDFLARE_TUNNEL_TOKEN dér. Hvis den læser .env fra projektmappen automatisk, skal feltet være tomt. Indsæt aldrig tokenet direkte i Compose-filen.
  5. Klik Deploy NowDocker henter images og bygger HMRDTM. Åbn bagefter projektet og kontrollér, at begge containere kører.
Kontrollér før deploy

Der må ikke være en ports:-sektion for HMRDTM. Appen bruger kun expose: 3000 internt; Cloudflare Tunnel er den eneste vej ind udefra.

Terminal (alternativ)
docker compose -f compose.production.yml up -d --build
Kontrollér status
docker compose -f compose.production.yml ps
docker compose -f compose.production.yml logs --tail=50 cloudflared
Det rigtige resultat

hmrdtm er healthy, tunnel-containeren kører, og loggen viser registrerede forbindelser uden gentagne fejl.

Backup i Docker-GUI

Vælg kommando ud fra din terminal

En terminal åbnet fra Docker-GUI kører inde i containeren. Den har ikke Docker-kommandoen installeret. Vælg shellen /bin/sh i GUI'en — HMRDTM bruger Alpine Linux, som ikke indeholder /bin/bash.

Beskyt ikke hele gæste-hostnamet med Access, da invitationslinks ellers stoppes. Appens login beskytter /admin.

Én fælles konfiguration

.env, README og Compose hænger sammen

.env.example er facitlisten for produktionens private .env. Den skal kun indeholde Cloudflare-tokenet.

Låst i ComposeDATABASE_PATH, BACKUP_DIR og NODE_ENV.

07
Når noget driller

Seks hurtige fejltjek

502Bad Gateway +

Tjek at appen er healthy, og at service-URL'en er http://hmrdtm:3000 — ikke localhost.

OFFTunnel offline +

Tjek tunnel-logs, tokenet i .env og udgående TCP/UDP på port 7844.

DNSSiden findes ikke +

Kontrollér hostname og den publicerede applikationsrute i Cloudflare. Test derefter uden lokal Wi-Fi.

FILEpackage.json: EACCES +

En ældre Dockerfile — eller restriktive rettigheder fra NAS-uploadmappen — kan gøre package.json ulæselig for brugeren node. Opdatér projektets Dockerfile og byg et nyt image.

Sikker genopbygning

Behold mapperne data og backups. De er vedvarende data og må ikke slettes. I Docker-GUI: åbn projektet, vælg Stop, opdatér filerne i projektmappen, og vælg Build/Rebuild eller Deploy Now. En almindelig Start/Restart bruger det gamle image og løser ikke fejlen.

NAS/SSH-terminal (alternativ)
docker compose -f compose.production.yml up -d --build
LOGINAdmin findes allerede +

Det betyder, at databasen allerede har en administrator — ofte efter en tidligere opsætning. Gå tilbage til Log ind i stedet for Første admin, og brug den eksisterende e-mail og adgangskode.

Kun hvis adgangen er mistet

Tag først en backup. Kommandoen nedenfor nulstiller alle brugere, sessioner og eventejerskaber, men bevarer events og gæstedata. Åbn derefter /admin/login og vælg Første admin.

Docker-GUI → Terminal i hmrdtm-containeren
npm run db:backup
node -e "const Database=require('better-sqlite3'); const db=new Database('/app/data/app.db'); db.exec('DELETE FROM sessions; DELETE FROM admins'); console.log('Admin-adgang nulstillet')"

Fra en NAS/SSH-terminal sætter du docker compose -f compose.production.yml exec -T hmrdtm foran hver af de to kommandoer.

BUILDDocker kræver BuildKit +

Fejlen the --mount option requires BuildKit kommer fra en ældre Docker-builder, som ikke forstår RUN --mount. Projektets aktuelle Dockerfile er kompatibel med den klassiske builder og kræver derfor ikke, at BuildKit aktiveres.

Kopiér den nye Dockerfile til NAS'en

Overskriv den gamle Dockerfile i samme mappe som compose.production.yml. Hvis UGOS har gemt et tidligere build, skal app-imaget bygges igen uden cache.

NAS/SSH · byg helt forfra
docker compose --env-file .env -f compose.production.yml down
docker compose --env-file .env -f compose.production.yml build --no-cache hmrdtm
docker compose --env-file .env -f compose.production.yml up -d

I Docker-GUI skal du stoppe projektet, sikre at den opdaterede Dockerfile er valgt, og vælge en fuld genopbygning uden cache. Aktivering af BuildKit er stadig en mulig løsning på ældre Dockerfiles, men er ikke nødvendig med filen i dette projekt.

DBSQLite kan ikke åbnes +

SQLITE_CANTOPEN betyder normalt, at /app/data ikke findes, ikke er skrivbar for containerens node-bruger, eller at UGOS har fortolket det relative bind mount ./data fra en anden projektmappe.

Bevar eksisterende data

Brug aldrig docker compose down -v. Hvis data/app.db allerede findes og indeholder rigtige events, skal den sikkerhedskopieres, før mount eller volume ændres.

NAS/SSH · kontrollér den faktiske mount og skriveadgang
docker compose --env-file .env -f compose.production.yml run --rm \
  --entrypoint sh hmrdtm -c '
    echo "DATABASE_PATH=$DATABASE_PATH"
    id
    ls -ldn /app /app/data /app/backups
    su-exec node sh -c "touch /app/data/.write-test && rm /app/data/.write-test"
  '

Hvis testen fejler med Permission denied, kan de eksisterende bind mounts normalt repareres sådan:

NAS/SSH · ret bind-mount-rettigheder
mkdir -p data backups
docker compose --env-file .env -f compose.production.yml run --rm \
  --entrypoint sh hmrdtm -c '
    chown -R node:node /app/data /app/backups
    chmod -R u+rwX,go-rwx /app/data /app/backups
  '
docker compose --env-file .env -f compose.production.yml up -d --build
Hvis UGOS afviser chown eller bruger en ukendt relativ sti

Ved en ny installation uden en eksisterende database er Docker-managed volumes den mest robuste løsning. Docker styrer selv placering og rettigheder. Ved eksisterende data skal app.db først kopieres sikkert til det nye volume.

Compose · erstat de to bind mounts i hmrdtm-servicen
volumes:
  - hmrdtm_data:/app/data
  - hmrdtm_backups:/app/backups
Compose · tilføj på topniveau før networks
volumes:
  hmrdtm_data:
    name: hmrdtm_data
  hmrdtm_backups:
    name: hmrdtm_backups

networks:
  hmrdtm_internal:
    name: hmrdtm_internal

Genstart med docker compose down og derefter docker compose up -d --build — stadig uden -v. Det korrekte resultat er først Migrations applied og derefter Ready i loggen.
